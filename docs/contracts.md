# Native contract invariants

Catalogue entity keys are native `series_ticker`, `event_ticker` and `market_ticker`; relationships use declared parents. Settlement status and results are copied without conflating native states. Raw response bytes are authoritative acquisition evidence. JSON payloads preserve exact numeric values as strings when parsing JSON decimals; financial projections use exact decimals, and definitions include rules, strikes, price grids, settlement sources and native combo legs.

Catalogue current tables include `payload_json` for the complete observed object plus normalized identity/provenance. Unresolved parents remain visible through left joins. `combo_legs` has one row per native selected leg, keyed by combo market and leg index, and retains native side and settlement value. Observation history has one row per observed page item and JSON pointer, deduplicated by observation identity on replay. A catalogue v1 release is built from exactly one complete catalogue capture.

Event-embedded markets are observation references only. Direct live and historical market endpoints determine current market inventory; a nested event summary cannot override a direct market definition. A catalogue release covers completed requested traversals over an observation interval, not an atomic exchange snapshot or a proof of permanent absence.

Targeted bundles contain only found usable selected markets and their authoritative event/series parents. Every requested ticker appears exactly once in coverage; absent, malformed, unresolved and failed are distinct states. A malformed or failed response prevents completion, while honest absence/unresolved parent results may complete with non-found coverage. No producer warehouse is needed to verify or consume a copied bundle.

Release identity is the SHA-256 of compact sorted JSON (`separators=(",", ":")`, no trailing newline) of literal filename inventories. Inventory entry fields are `sha256` and integer `size`; filenames and digests are ASCII. File SHA-256 includes every byte, including JSON files' final newline. Catalogue/metadata manifests have separate versioned contract identifiers.

## Storage and publication formats

These are separate compatibility boundaries for compressed receipts, journal recovery and composed catalogue releases. Existing catalogue v1 and metadata v1 behavior remains supported.

### Operator roots and rollback

The legacy root marker is exactly `{"owner":"oddsfox.kalshi.events.v1"}`; storage version 2 adds `"storage_version":2`. New exchange-wide operator roots use `{"owner":"oddsfox.kalshi.events.v1","storage_version":3}` in `root.json`. Dedicated series roots use version 4 as described below. Older binaries reject unsupported markers before writing. Storage version, journal version, acquisition protocol and release contract are separate boundaries.

Updated binaries read version 1 and 2 roots and their existing artifacts. Writing to either requires the explicit `upgrade-root` command. Upgrade takes the canonical writer lock, checks the marker again under that lock, and atomically replaces only `root.json`; it does not rewrite evidence, captures, journals, builds, publications or the logical root identity. Every writer rechecks the marker after locking. An incomplete older capture resumes using its original acquisition and checkpoint protocols, including original parameters on parent tasks discovered after upgrade.

The first v2 catalogue operation creates `root-id.json`, a stable logical root identity used by composed lineage. A whole-root copy retains that identity; copying unrelated composed artifacts into another root does not establish valid ancestry. The storage marker itself remains unchanged.

Stop writers before upgrading an existing root. Initial rollout uses a separate operator root. Binary rollback uses a separate legacy root and a retained verified v1 publication. Never downgrade the marker or allow an old binary to write an upgraded root.

### Raw HTTP receipts

Raw evidence preserves the exact encoded HTTP entity bytes, excluding HTTP transfer framing. Identity encoding remains the default; `--compression identity|gzip` makes gzip an explicit operator choice. An identity response is valid when gzip was requested. Only identity and a single gzip member are supported. Unsupported encodings, incomplete gzip streams, checksum failures, additional members and trailing bytes are rejected as unusable evidence.

Receipt v1 remains readable with its identity-body `size` and `sha256`. Compressed evidence uses receipt v2 and records its content encoding plus the encoded and decoded sizes and SHA-256 checksums. Readers verify both representations before accepting a compressed payload. Encoding does not change the decoded JSON semantics, decimal preservation or observation identity rules.

Each capture seals independent encoded and decoded response ceilings at creation; both initially use the existing response-limit setting. A small encoded body does not excuse excessive decoded expansion. Download accounting measures actual encoded bytes received, including unsuccessful attempts and retries. Streaming and decompression retain aggregate in-flight reservations, disk limits, deadlines, origin validation, the shared request limiter and existing retry guarantees. The normal rate remains 10 requests per second; capability and rate diagnostics are bounded, explicitly invoked operations.

Bodies stream into atomic temporary evidence files while being hashed. Durability order is raw body, usable receipt, durable journal transition, then applied capture state. Failed or partial attempts cannot become usable receipts. Recovery includes partial temporary files and interrupted reservations in storage accounting.

Atomic metadata replacements account for the full temporary replacement while retaining the original allocation. Capacity checks, writes and accounting serialize across workers. Directory creation synchronizes each new entry in its parent before a child can be committed; retries synchronize the nearest existing ancestor's parent again to cover an interrupted prior synchronization. Shared request cooldowns are checked again after every wait, including deferrals received while a worker was already waiting.

On the MacBook, file synchronization uses `fsync` and directory synchronization opens and synchronizes the directory itself. Failed barriers prevent successful progression; raw → receipt → journal ordering remains unchanged. Paths reject symlinks, including symlink ancestors. Persisted receipt and evidence inventory paths use forward slashes. This platform-support removal changes no storage, catalogue or metadata version.

### Journal recovery

New captures use a versioned append-only journal. Records have monotonic sequence numbers and chained integrity checks; an atomic snapshot records its replay offset. Every committed page retains a durable append. Snapshots occur every 100 transitions, at completion and at an orderly budget stop. This amortizes snapshots without removing file or directory synchronization guarantees.

The journal covers all recovery-relevant state: sealed settings, pagination cursors and loop detection, cursor resets and generations, historical-cutoff phases, discovered parent tasks, coverage and completion. Replay after the snapshot offset is idempotent. A committed raw receipt orphaned before its transition is recovered without repeating its request.

New exchange-wide and targeted captures seal `acquisition_protocol: 3` in their journal state; scoped series captures seal protocol 4. An absent field selects the original acquisition behavior; unknown values and booleans are invalid. Genesis, snapshots, control transitions and receipt recovery bind the chosen protocol. This does not change journal framing version 2.

Only an incomplete trailing record lacking its commit delimiter may be discarded. Interior corruption, invalid checksums, missing sequences and contradictory transitions fail closed. Legacy captures retain their original checkpoint and page-journal protocol, including after a root upgrade.

The v2 snapshot remains `captures/<capture_id>/state.json`. Its envelope contains `version`, `capture_id`, logical `state`, `seen_cursors`, `state_sha256`, `snapshot_sha256` and `_journal` (`seq`, `offset`, `sha256`, `transition_count`). The journal checkpoint binds a digest of both logical state and cursor history; recomputing a snapshot's own checksum cannot replace that anchored state. The offset is the byte position after the anchored record's newline.

`pages.jsonl` records contain `version`, `capture_id`, `seq`, `prev`, `op`, `payload` and `sha256`. Each checksum covers canonical JSON excluding its own `sha256` field. The first `start` record has sequence 1 and a previous checksum of 64 zeroes. Page and bounded control transitions increment the transition count; checkpoint records do not. Readers validate the complete chain and snapshot anchor before accepting recovered state, then apply only the suffix after the snapshot. A valid genesis permits recovery when the first snapshot was never written. An existing invalid snapshot is rejected.

Read-only inspection never repairs evidence. Resume takes the canonical writer lock before truncating an undelimited trailing record and syncs the truncation. Never edit a journal or snapshot by hand; preserve the root and investigate a committed-record integrity error instead of discarding it.

### Selected acquisition and parent hydration

Protocol 3 partitions selected market tickers deterministically into live `/markets` requests with at most 100 tickers and 6,144 bytes in the encoded initial URL. The initial-URL bound excludes subsequently supplied pagination cursors; existing cursor and response ceilings still apply. These tasks do not enumerate a reconciliation scope. Every returned ticker must belong to its requested batch.

Coverage accumulates across a batch's pages and resets when its pagination generation restarts. Only the final generation determines omissions. Its terminal page durably creates deduplicated singular live lookups for missing tickers. A live 404 then schedules the existing historical lookup; authoritative historical absence establishes absent coverage. List omission and collection errors never establish absence. Earlier-generation observations remain evidence and history. Parent hydration can downgrade a currently found selection to unresolved; it preserves definitive absent coverage established by the live/historical 404 chain, even when retained observations have unavailable parents.

New protocol-3 event-parent lookups request `exclude_markets=true`, preserving native event definitions and series relationships while omitting incidental child markets. Existing receipts, including embedded child observations, remain readable and unchanged. Direct market traversals still establish full catalogue coverage. Batching changes source endpoints, receipt and observation identities for newly acquired selections; provenance always names the actual request rather than a synthetic individual lookup. Metadata output preserves the operator's selection order.

### Landing and incremental query work

Landing uses the existing dlt Parquet/DuckDB merge keyed by observation identity, with explicitly typed Arrow tables. Application batches flush at 4,096 rows or 8 MiB of logical UTF-8 field data; an oversized observation is emitted alone. The byte target is soft for that singleton, not a new evidence rejection threshold or hard memory quota. Scoped dlt lineage generation preserves compatibility with existing dictionary-created warehouses, and extraction/normalization buffers flush each yielded batch. Configuration is restored after success or failure.

The 13 logical landing columns retain text types and nullability. Provider timestamp conversion retains the dictionary loader's logical results; complex values remain in the complete native payload with a null projected timestamp. Physical database bytes and dlt internal identifiers are not public release identities. The documented dlt post-load storage-quota limitation remains.

Incremental current-entity winner windows restrict their input to affected keys while reading all history for each key. Required-parent membership, dependency discovery, full integrity tests and complete exports remain unchanged. Full-mode query branches retain their existing behavior.

### Catalogue versions and selection

Catalogue v1 remains `oddsfox.kalshi.catalogue.v1`, published through `current.json`. Full capture remains the default. Default `load`, `build`, `publish` and metadata capture selection excludes incremental captures, even if a delta is newer. Targeted captures remain separate from catalogue captures.

Opt-in `capture --incremental` pins a certified v2 publication when present, otherwise a certified v1 baseline. Building or publishing a composed capture requires its explicit capture ID. Composed output uses `oddsfox.kalshi.catalogue.v2` and `current-v2.json`; promotion leaves `current.json` untouched. A verified full capture published as version 2 establishes a new baseline.

`current`, `replay`, `rebuild` and `publish` accept `--catalogue-version 1|2`, defaulting to 1. `verify --release` dispatches from the supplied manifest contract. Metadata v1 export rejects incremental captures instead of exporting only their changed subset. Full exports, checksums and independent release verification remain required for both catalogue versions. A pre-existing release destination must match its contract and capture identity as well as its verified files.

A v2 manifest additionally carries `root_id`, `baseline_release_id`, `baseline_manifest_sha256`, `baseline_capture_id`, `previous_watermark`, `watermark_started_at`, `delta_depth` and `membership_sha256`. Baseline fields name the immediate pinned predecessor for a delta and are null for a full rebase. Full depth is zero; each delta increments depth. The membership digest commits sorted scope/entity-kind/native-ticker entries, including membership not visible in the current relations. These fields are also included in v2 coverage, binding them into the release identity. Publication pointers contain the release ID and manifest checksum.

Every release contract binds `capture_id` and `coverage_scope` from its single-row coverage relation to the manifest: catalogue v1/v2 require `catalogue`, and series v1 requires `series`. Verification reads only the bounded primitive columns after checking the file inventory, and rejects missing columns, invalid types, extra rows or mismatched values. V2 and series v1 additionally bind all eight lineage fields; series v1 also binds its ticker and `include_multivariate` flag. Publication time and the optional physical warehouse checksum are outside this coverage binding. This strengthens standalone verification without changing compatible release bytes or schemas.

New v2 manifests also record the optional `warehouse_sha256` of the freshly certified, checkpointed database. It is a verification hint outside the release identity and coverage fields. Matching freshly verified database bytes avoid a repeated semantic comparison; a missing or different hash requires schema, row-multiset and membership equivalence against the pinned release. Existing v2 manifests remain valid and immutable. V1 manifests do not gain this field.

### Coordinated refresh results

`refresh [--full | --capture-id ID]` is an additive catalogue-v2 workflow. It uses existing capture/build/publication checkpoints and one operator lock and deadline; it adds no storage, journal, receipt or acquisition format. Default invocation requires a verified baseline, preferring v2 with the existing v1 fallback. Full acquisition and rebasing require explicit `--full`; eight deltas never trigger an automatic rebase. Targeted captures cannot be resumed through this command. Existing capture, publication and metadata commands retain their selection defaults and result schemas.

The new workflow result distinguishes whole-operation `complete`, nullable `capture_complete`, allocated `capture_id`, nullable `resumable`, stage, publication state and acquisition accounting. Stages are `preflight`, `capture`, `publication`, `complete`; publication includes build, export, verification and pruning. Publication state is `not_attempted`, `verified` or `unknown`. Unknown counts remain null with incomplete accounting. An allocated ID does not prove durable genesis. Successful completion includes the verified release identity and output directory. All expected operational failures, including setup and final reconciliation, retain one structured result and the known identity. Argument-parser errors retain normal argparse behavior.

A budget stop returns exit 3 even when acquisition completed. Other invariant/input failures return exit 1. Publication/cleanup failure may follow pointer promotion and reports unknown state rather than promising rollback; retrying the same explicit ID follows existing recovery. The v1 pointer remains untouched. No new workflow command performs live tuning, changes rates automatically, or weakens evidence verification.

### Incremental acquisition and freshness

Each incremental capture seals a UTC start watermark before its first request. Its ordinary-event and supported non-combo market metadata queries begin at the previous published watermark minus a fixed 300-second overlap. Series, combo events, combo markets and historical markets are fully reconciled on every composed refresh. The watermark advances to the sealed start only after verified publication. Resume retains the original baseline, watermark and query window even if another publication appears.

The first delta from a v1 baseline seeds its previous watermark from that full capture's UTC `started_at`. A full v2 rebase uses the same seed. Completion or manifest timestamps would miss changes made during the baseline traversal.

Overlap deduplicates an observation already identified by the same receipt and observation identity. Distinct receipts remain distinct historical observations; equal ticker or payload values alone are not a deduplication key. Every historical-cutoff receipt remains part of the evidence history, including cutoffs before subsequent historical reads.

Metadata-update filters are not a universal change feed. Trading-only values such as price, volume and open interest may be carried from the baseline with their actual observation timestamps. Updates arriving outside the overlap may require full reconciliation or rebase. Coverage describes the acquired scopes and interval; it does not claim a fresh atomic snapshot of all values.

### Membership, projections and provenance

A composed build copies the certified, checkpointed baseline warehouse into staging. The published baseline is immutable. New observations land idempotently; affected current entities, relationships and dependent combo legs are updated, and full integrity tests still run.

Membership is an explicit input to current projections, distinct from observation history and parent-resolution lookups. A completed full reconciliation replaces only its own scope's membership. If a traversal resets its cursor, only its final completed cursor generation establishes replacement membership; earlier receipts remain observations and evidence. An incomplete traversal cannot remove members. Omission from a delta removes nothing.

Applicable live and historical market memberships are combined before resolving current markets. Removal from current membership retains observation history; reappearance can restore membership. Parent hydration resolves declared relationships without claiming that a lookup enumerated an entire reconciliation scope. Reassignment updates the affected relationship and dependent combo legs.

Current events include listed event membership plus authoritative parents of active markets positively resolved during this capture. Current series include listed series membership plus authoritative parents of active events positively resolved during this capture. A prior observation alone is not a successful fresh parent lookup; a 404 does not restore parent eligibility. Lookup-only parents reachable solely from inactive historical rows do not become permanent members. Removing historical membership does not remove a market still retained by live membership; delta omission supplies no live tombstone, so authoritative removal in that case requires a full rebase.

Current winners remain `received_at DESC, observation_id DESC`. Provider timestamps never silently replace that order. Direct market definitions remain authoritative over event-embedded references. Carried and new rows retain their original source capture, receipt and observation provenance; carried evidence is never relabeled as newly acquired.

Full v2 baselines project the final completed cursor generation's memberships into their own certified warehouse under `builds-v2/<capture_id>`; the v1 warehouse remains unchanged. When a legacy full capture lacks fresh parent-resolution evidence needed by that projection, a new full capture is required. A direct v1 bootstrap preserves the pinned v1 current ordinary events and live non-combo markets with successful non-singular list evidence, including earlier cursor generations; singular hydration and history-only markets cannot seed those scopes. This preserves the selected baseline's semantics until a scope is explicitly reconciled.

Baseline copying requires a closed, checkpointed certified warehouse. Rebuilding the same baseline may change database bytes; accepting that rebuild still requires fresh certification, schema and row-multiset equivalence against the pinned immutable release, and equivalent membership state. Published source databases are never opened for writable checkpointing. Carrying a baseline does not relabel its evidence as newly acquired.

### Ancestry, retention and discard

A composed baseline permits at most eight delta captures. Another delta requires a verified full rebase. Missing, cyclic, corrupted or cross-root ancestry is rejected before build or publication.

Retention preserves the complete evidence closure reachable from both publication pointers and incomplete captures. Incomplete captures stay pinned indefinitely unless explicitly discarded. Retained completed compositions also keep their referenced ancestry. Completed captures at or after the relevant full baseline start remain candidates for publication; an older unreachable group may be pruned together, with children retired before parents. No incomplete recovery pin expires merely because time elapsed.

Explicit discard is allowed only for an incomplete capture that no publication or descendant references. Pruning computes the retained dependency closure before deleting anything, and removes obsolete dependencies only after successful verification and promotion. A failed build, verification or promotion cannot prune evidence needed by either publication or recovery.

### Ordinary-series releases

A dedicated root fixes exactly one descriptor: `{"kind":"series","series_ticker":"KXCPI","include_multivariate":false}`. The selected ticker is validated rather than hardcoded. Its `root.json` contains the existing owner, `storage_version: 4` and this `scope`. Initialization requires a new empty directory and installs the marker under the canonical writer lock. Competing initializers cannot replace another scope or an ordinary marker. Writers recheck the exact descriptor after locking. Version 3 remains the default for ordinary roots; no populated root can be converted or marker downgraded. If initialization stops before the marker, an unowned directory containing a lock file fails closed; preserve it and use a fresh directory.

Protocol 4 is valid only with this exact scoped profile. Genesis, immutable journal settings, snapshots, request identities, usable receipt contexts, certification and baseline pins bind the scope and logical root identity. Missing fields, extra fields, non-boolean multivariate flags, changed tickers, incompatible copied captures and unsupported contracts fail closed. Journal framing, raw formats and raw → receipt → journal → state durability remain unchanged. Existing ordinary captures retain their original protocols and request parameters.

Both baseline and subsequent refresh acquisition enumerate `/series/{ticker}`, `/events?series_ticker=S&with_nested_markets=false&limit=200`, `/markets?series_ticker=S&mve_filter=exclude&limit=1000` and `/historical/markets?series_ticker=S&limit=1000`, plus the existing historical-cutoff protocol. Every cursor is followed, without status or update-time filters. No global series or multivariate traversal is used. See Kalshi's [events](https://docs.kalshi.com/api-reference/events/get-events), [markets](https://docs.kalshi.com/api-reference/market/get-markets) and [historical markets](https://docs.kalshi.com/api-reference/historical/get-historical-markets) contracts. During live acceptance the historical endpoint rejected combining `series_ticker` with `mve_filter` as mutually exclusive, so its scoped query uses the series filter alone; strict ordinary-event and combo validation still applies.

The singular series must exist and match. Events must identify the selected series and cannot carry combo payloads. Current markets must resolve through authoritative event definitions, not ticker prefixes. Missing, contradictory or out-of-scope parents preserve evidence but prevent publication. Fresh proof covers parents required by retained-history winners as well as incoming observations, including equal receipt times and clock rollback. Singular event hydration suppresses incidental children. Only final pagination generations replace membership; earlier verified observations remain history and cutoff history stays complete.

Scoped refreshes use certified predecessor copies and the existing Arrow, affected-key, relationship and full-integrity machinery. Unlike exchange-wide metadata deltas, every completed series membership scope is replaced, including live events and markets. Combined live/historical membership determines current markets. Observation history, exact decimals, source provenance and last-observed/direct winner ordering remain unchanged. Distinct newly fetched receipts create observations even for unchanged objects; identical-receipt replay is idempotent. There are no metadata-update windows or `query_from` fields. Lineage timestamps remain for ordering and certification, not filtered acquisition.

The public contract is `oddsfox.kalshi.series.v1`, through `current-series.json` only. It reuses the internal v2 warehouse layout and deterministic relations without creating catalogue v3. Manifest and coverage both bind `coverage_scope: "series"`, `series_ticker` and boolean `include_multivariate: false`, alongside the existing lineage fields; the manifest also carries `series_scope`. Standalone `verify --release` dispatches explicitly by contract and checks this binding. Unknown contracts never fall through to catalogue v1. Series baseline selection has no catalogue-v1 fallback. All ancestry must have the same contract, root identity and exact scope.

`series refresh --series-ticker S --full` initializes the baseline. Later `series refresh` reconciles it; `series refresh --capture-id ID` resumes its exact settings and pinned predecessor. `--full` and `--capture-id` conflict. Results use the existing refresh stage/publication/accounting/exit semantics plus `series_scope`; an allocated capture ID alone does not prove durable initialization. One writer lock and deadline cover all stages. Completed resume avoids networking and redundant landing while retaining fresh verification. `series current`, `series replay [--capture-id ID]` and `series rebuild` select the series publication; replay/rebuild do not publish. Generic status and discard remain scope-aware, while ordinary catalogue and metadata producer commands reject these roots.

Eight refresh captures require an explicit full rebase before another. Retention protects the series publication closure and incomplete pins, with no time-based expiry. A verified promotion may prune obsolete unreferenced ancestry after rebasing; it does not promise permanent history beyond protected ancestry. Cleanup can fail after pointer promotion, so unknown publication state requires inspection/retry, not assumed rollback. Preserve the root on committed corruption. Old binaries cannot write version 4 roots or consume this new contract; rollback uses a separate compatible root and retained verified publication, never a downgraded marker.

Coverage remains `atomic_snapshot: false`. Kalshi separates live and historical market tiers while events and series stay at their original endpoints ([historical-data documentation](https://docs.kalshi.com/getting_started/historical_data)). A handoff during separate paginated reads can change visibility. Completed traversals certify the declared scope over the observation interval, not an atomic exchange snapshot or exposure of every historically existing record. Further reconciliation may be needed near a handoff. Incremental persistence does not reduce series acquisition work or guarantee a faster build; complete exports and verification remain required.

### Deterministic output and verification

Certified output proves the export keys unique: native ticker for current series/events/markets; observation ID for history; combo market ticker and leg index for combo legs; parent kind/ticker and child kind/ticker for relationships. Publication orders by those explicit keys, preserving existing lexicographic order where they are already a unique prefix. Payloads, decimal types, relation schemas and Parquet writer settings remain unchanged for compatible full-mode output.

Within one command, evidence validation, hashing, decoding, landing and inventory collection may share verified input bytes. This is not a cross-command trust cache: publish freshly verifies build evidence and checksums, while standalone verification remains independent and complete. Mutation between commands must prevent publication. Metrics and benchmark reports stay outside command-result JSON, evidence, release identities, Git and distributions.

### Diagnostic partition evidence

The manual throughput probe can acquire explicitly selected ordinary-series and multivariate-collection event partitions into fresh ordinary operator roots. These are diagnostic receipts, not captures: no genesis, snapshot, page journal, warehouse, release or publication pointer is created. Receipt context uses diagnostic identifiers and cannot satisfy production capture/task identities. Normal build, replay, metadata export and publication cannot select this evidence. The pilot is non-resumable; preserve incomplete evidence and use a new output directory for another experiment.

Ordinary partitions use `/events?series_ticker=S`; multivariate partitions use `/events/multivariate?collection_ticker=C`. Both request 200 events per page, disable nested markets and follow all returned cursors without status/update filters. One shared client, limiter and budget serve at most eight workers, with at most one request outstanding per partition. Repeated cursors, malformed envelopes or identities, contradictory scope and unexpected statuses stop the experiment; this pilot does not reset cursors.

Preflight retrieves each selected collection definition once and binds its native ticker and series to the shared selection. Returned ordinary events must match their series; collection-filtered events must match the declared series and any supplied collection identifier. Collection membership remains a provider-filter assertion, not independent certification. Constituent `associated_event_tickers` do not establish generated-event membership. Duplicate observations and payload variants remain in diagnostic inventories; fingerprints distinguish numeric decimals from equal-looking strings and canonicalize object-key ordering. An incomplete traversal never proves absence.

Report version 2 identifies the throughput profile; existing screening reports retain version 1. Diagnostic verified pages are distinct from production journal-committed pages. Malformed or out-of-range worker reports stop further samples with unavailable accounting; unrepresentable derived rates are null. Reports and metrics are external to catalogue contracts, evidence identities and distribution contents. No storage version, acquisition protocol, release schema or production traversal changes through this pilot.
