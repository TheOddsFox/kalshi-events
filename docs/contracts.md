# Native contract invariants

Catalogue entity keys are native `series_ticker`, `event_ticker` and `market_ticker`; relationships use declared parents. Settlement status and results are copied without conflating native states. Raw response bytes are authoritative acquisition evidence. JSON payloads preserve exact numeric values as strings when parsing JSON decimals; financial projections use exact decimals, and definitions include rules, strikes, price grids, settlement sources and native combo legs.

Native tickers are preserved exactly, with a local bound of 1–256 printable Unicode code points. Backslashes, non-U+0020 Unicode whitespace, other non-printable characters, leading ASCII spaces, leading/trailing slashes, and empty or `.`/`..` slash-delimited segments are rejected. Trailing U+0020 spaces are retained exactly and encoded as `%20` in singular lookup paths; previously accepted interior-space endpoint spellings remain unchanged. Other printable punctuation is native data, including commas, literal `%`, `?`, `#`, quotes and leading hyphens. Comma-containing selected markets and parent identities use existing singular lookups because the API batch filter uses commas as delimiters; comma-free request plans remain unchanged. A comma inside one CLI value remains part of that one identifier. Raw endpoint query and fragment delimiters remain invalid. Singular request paths apply canonical percent encoding once; parent authority decodes the expected path segment once. For example, native `A/B` uses `A%2FB`, while native `A%2FB` uses `A%252FB`, and native `KXLALIGAGOAL-26SEP19OSARVC-RVCPDÍAZ4-1` uses `KXLALIGAGOAL-26SEP19OSARVC-RVCPD%C3%8DAZ4-1`. Payload identities and batch selections retain their original text. Previously accepted ticker endpoint spellings remain unchanged.

Catalogue current tables include `payload_json` for the complete observed object plus normalized identity/provenance. Unresolved parents remain visible through left joins. `combo_legs` has one row per native selected leg, keyed by combo market and leg index, and retains the provider's exact side spelling (`yes`/`no` or `YES`/`NO`) and settlement value. Observation history has one row per observed page item and JSON pointer, deduplicated by observation identity on replay. A catalogue v1 release is built from exactly one complete catalogue capture.

Event-embedded markets are observation references only. Direct live and historical market endpoints determine current market inventory; a nested event summary cannot override a direct market definition. A catalogue release covers completed requested traversals over an observation interval, not an atomic exchange snapshot or a proof of permanent absence.

Targeted bundles contain only found usable selected markets and their authoritative event/series parents. Every requested ticker appears exactly once in coverage; absent, malformed, unresolved and failed are distinct states. A malformed or failed response prevents completion, while honest absence/unresolved parent results may complete with non-found coverage. No producer warehouse is needed to verify or consume a copied bundle.

Release identity is the SHA-256 of compact sorted JSON (`separators=(",", ":")`, no trailing newline) of literal filename inventories. Inventory entry fields are `sha256` and integer `size`; filenames and digests are ASCII. File SHA-256 includes every byte, including JSON files' final newline. Catalogue/metadata manifests have separate versioned contract identifiers.

## Storage and publication formats

These are separate compatibility boundaries for compressed receipts, journal recovery and composed catalogue releases. Existing catalogue v1 and metadata v1 behavior remains supported.

### Operator roots and rollback

The legacy root marker is exactly `{"owner":"oddsfox.kalshi.events.v1"}`; storage version 2 adds `"storage_version":2`. Storage version 3 is the former ordinary-root format and version 4 the former scoped-series format. New ordinary roots use the closed marker `{"owner":"oddsfox.kalshi.events.v1","storage_version":5}`. New scoped roots add their exact immutable `scope` descriptor to that version-5 marker. Other keys and malformed scopes are rejected. Older binaries reject unsupported markers before writing. Storage version, journal version, acquisition protocol and release contract are separate boundaries.

Updated binaries read version 1–4 roots and their existing artifacts. Writing to any requires the explicit `upgrade-root` command. Upgrade takes the canonical writer lock, checks the marker and exact scope again under that lock, and atomically replaces only `root.json`; it does not rewrite evidence, captures, journals, builds, publications or the logical root identity. Every writer rechecks the marker after locking. An incomplete older capture resumes using its original acquisition, compression, rate and checkpoint policies, including original parameters on parent tasks discovered after upgrade. Never downgrade a marker; rollback uses a separate legacy root and a retained verified publication.

The first v2 catalogue operation creates `root-id.json`, a stable logical root identity used by composed lineage. A whole-root copy retains that identity; copying unrelated composed artifacts into another root does not establish valid ancestry. The storage marker itself remains unchanged.

Stop writers before upgrading an existing root. Initial rollout uses a separate operator root. Binary rollback uses a separate legacy root and a retained verified v1 publication. Never downgrade the marker or allow an old binary to write an upgraded root.

### Raw HTTP receipts

Raw evidence preserves the exact encoded HTTP entity bytes, excluding HTTP transfer framing. New protocol-5 captures request gzip by default; `--compression identity` selects identity explicitly. An identity response is valid when gzip was requested. Only identity and a single gzip member are supported. Unsupported encodings, incomplete gzip streams, checksum failures, additional members and trailing bytes are rejected as unusable evidence. Legacy and resumed captures keep their sealed encoding.

Receipt v1 remains readable with its identity-body `size` and `sha256`. Compressed evidence uses receipt v2 and records its content encoding plus the encoded and decoded sizes and SHA-256 checksums. Readers verify both representations before accepting a compressed payload. Encoding does not change the decoded JSON semantics, decimal preservation or observation identity rules.

Each capture seals independent encoded and decoded response ceilings at creation; both initially use the existing response-limit setting. A small encoded body does not excuse excessive decoded expansion. Download accounting measures actual encoded bytes received, including unsuccessful attempts and retries. Streaming and decompression retain aggregate in-flight reservations, disk limits, deadlines, origin validation, the shared request limiter and existing retry guarantees. The default initial rate ceiling is 5 requests per second. Capability and rate diagnostics are bounded, explicitly invoked operations.

Bodies stream into atomic temporary evidence files while being hashed. Durability order is raw body, usable receipt, durable journal transition, then applied capture state. Failed or partial attempts cannot become usable receipts. Recovery includes partial temporary files and interrupted reservations in storage accounting.

Atomic metadata replacements account for the full temporary replacement while retaining the original allocation. Capacity checks, writes and accounting serialize across workers. Directory creation synchronizes each new entry in its parent before a child can be committed; retries synchronize the nearest existing ancestor's parent again to cover an interrupted prior synchronization. Shared request cooldowns are checked again after every wait, including deferrals received while a worker was already waiting.

Full storage reconciliation fails on unreadable paths and observes the invocation deadline; an unsuccessful inventory does not replace the previous ledger with partial counts. Request pacing is applied after durable attempt preparation, immediately before HTTP dispatch. These checks do not provide hard enforcement against third-party database writes.

On the MacBook, file synchronization uses `fsync` and directory synchronization opens and synchronizes the directory itself. Failed barriers prevent successful progression; raw → receipt → journal ordering remains unchanged. Paths reject symlinks, including symlink ancestors. Persisted receipt and evidence inventory paths use forward slashes. This platform-support removal changes no storage, catalogue or metadata version.

### Journal recovery

New captures use a versioned append-only journal. Records have monotonic sequence numbers and chained integrity checks; an atomic snapshot records its replay offset. Every committed page retains a durable append. Snapshots occur every 100 transitions, at completion and at an orderly budget stop. This amortizes snapshots without removing file or directory synchronization guarantees.

The journal covers all recovery-relevant state: sealed settings, pagination cursors and loop detection, cursor resets and generations, historical-cutoff phases, discovered parent tasks, coverage and completion. Replay after the snapshot offset is idempotent. A committed raw receipt orphaned before its transition is recovered without repeating its request. Each page change is verified and derived before journal append, then applied after the durable append; a post-append failure marks state uncertain and blocks further commits until recovery.

New ordinary and scoped captures seal `acquisition_protocol: 5` in their journal state; targeted metadata captures also use protocol 5. Protocol 3, protocol 4, and captures without an explicit protocol remain readable and resume with their original behavior. Unknown protocol values and booleans are rejected. Protocol-5 policy values for compression, rate adjustment, parent hydration and cutoff checkpoints are immutable, hashed into capture settings and checked during replay and receipt validation. Protocol-5 captures created during the staged rollout may seal `identity`/`fixed` or earlier `singular-v1`/`per-page-v1` policies; readers continue honoring those values rather than reinterpreting them. Genesis, snapshots, control transitions and receipt recovery bind the chosen protocol and policies. This does not change journal framing version 2 or catalogue/metadata/series release contracts.

The current protocol-5 defaults request gzip and use `decrease-on-429`; `--compression identity` and `--rate-policy fixed` are explicit alternatives. The shared adaptive limiter starts at the operator's `--max-rate` ceiling (5 requests/second by default), halves once on the first 429 from each limiter generation, and never falls below `min(initial ceiling, 0.25 requests/second)` or increases within an invocation. It honors `Retry-After`; waiting workers recheck the new spacing and cooldown. A manual resume starts from its supplied ceiling, so the previous invocation's effective lowered rate is not persisted.

#### Private legacy exchange-profile full-capture recovery index

Only unscoped, non-incremental protocol-5 full captures may use the private persistent SQLite parent index. It is enabled only when the operator root already has a validated logical root ID. Without that ID, resume still prioritizes acquisition before reconstructing older receipts with the disposable index; the cache never creates an ID or changes capture, receipt or request identities to enable itself. If directory permissions prevent creating a private cache, acquisition uses the disposable index without changing those permissions or leaving a capture cache behind. Existing unsafe cache files and links still fail closed. The index is an auxiliary hint, not raw evidence, an authorization to publish, or a certification result.

Each durable index checkpoint binds the logical root ID, capture ID and sealed settings, acquisition protocol, normalization version, and the exact journal sequence/offset/digest anchor. Its rows describe an ordered prefix of journal pages whose receipts were verified before indexing. Resume validates snapshot, journal and sealed settings first, then prioritizes available acquisition requests; it advances the older receipt-index backlog in journal order when the scheduler has room. Acquisition-first ordering depends on a validated snapshot; if it is absent, recovery may need to replay the full authoritative journal before networking begins. The index checkpoint is a separate soft trigger at 100 indexed pages or five seconds, checked between pages. A single large receipt can exceed that interval; journal append, snapshots and raw-before-journal durability are unchanged.

The cache may be discarded and rebuilt if absent, stale, ahead of the journal, incompatible or corrupt. These conditions affect the cache only. If recognized SQLite corruption interrupts application after a durable page append, the same invocation rereads authoritative journal state before rebuilding the index and reconciling orphan receipts; it never clears uncertainty by trusting partially applied memory. Invalid settings, journal anchors, receipts or raw evidence still fail closed. Completion requires a clean index derived from receipts freshly verified in the current invocation plus a freshly verified parent closure. A warm cache is reset before that pass, never upserted as final authority. A cold clean accumulator may be reused when it already contains the verified ordered prefix. Legacy, targeted, scoped-series and incremental captures retain their existing recovery behavior. Published builds keep their independent verification path.

A stale or semantically changed warm hint can lead to provisional parent lookups, but the scheduler issues them only after primary tasks and pending known hydration are exhausted; these are bounded real API requests, not cache-derived observations. Only freshly validated responses become observations kept in history; their rows enter current entities only when verified membership or parent closure requires them—cache-only facts never land. Because full acquisition is not an atomic snapshot, a valid parent response can arrive after its listing page without indicating corruption.

Recovery timing is measured separately from supervisor setup and is not a completion or performance guarantee. The paired small-fixture results and remaining scale gates are recorded in [performance guidance](performance.md#supervised-production-acceptance).

The scheduler has at most eight submitted futures and one outstanding request per traversal, and requeues unfinished traversals fairly. It prepares a page-local transition, durably appends it, then applies it. Snapshots still occur every 100 transitions and at completion or an orderly budget stop. These limits bound scheduled work; they do not weaken durability or remove full catalogue coverage.

Only an incomplete trailing record lacking its commit delimiter may be discarded. Interior corruption, invalid checksums, missing sequences and contradictory transitions fail closed. Legacy captures retain their original checkpoint and page-journal protocol, including after a root upgrade.

The v2 snapshot remains `captures/<capture_id>/state.json`. Its envelope contains `version`, `capture_id`, logical `state`, `seen_cursors`, `state_sha256`, `snapshot_sha256` and `_journal` (`seq`, `offset`, `sha256`, `transition_count`). The journal checkpoint binds a digest of both logical state and cursor history; recomputing a snapshot's own checksum cannot replace that anchored state. The offset is the byte position after the anchored record's newline.

`pages.jsonl` records contain `version`, `capture_id`, `seq`, `prev`, `op`, `payload` and `sha256`. Each checksum covers canonical JSON excluding its own `sha256` field. The first `start` record has sequence 1 and a previous checksum of 64 zeroes. Page and bounded control transitions increment the transition count; checkpoint records do not. Readers validate the complete chain and snapshot anchor before accepting recovered state, then apply only the suffix after the snapshot. A valid genesis permits recovery when the first snapshot was never written. An existing invalid snapshot is rejected.

Read-only inspection never repairs evidence. Resume takes the canonical writer lock before truncating an undelimited trailing record and syncs the truncation. Never edit a journal or snapshot by hand; preserve the root and investigate a committed-record integrity error instead of discarding it.

### Selected acquisition and parent hydration

Protocol 3 partitions selected market tickers deterministically into live `/markets` requests with at most 100 tickers and 6,144 bytes in the encoded initial URL. The initial-URL bound excludes subsequently supplied pagination cursors; existing cursor and response ceilings still apply. These tasks do not enumerate a reconciliation scope. Every returned ticker must belong to its requested batch.

Coverage accumulates across a batch's pages and resets when its pagination generation restarts. Only the final generation determines omissions. Its terminal page durably creates deduplicated singular live lookups for missing tickers. A live 404 then schedules the existing historical lookup; authoritative historical absence establishes absent coverage. List omission and collection errors never establish absence. Earlier-generation observations remain evidence and history. Parent hydration can downgrade a currently found selection to unresolved; it preserves definitive absent coverage established by the live/historical 404 chain, even when retained observations have unavailable parents.

New protocol-3 event-parent lookups request `exclude_markets=true`, preserving native event definitions and series relationships while omitting incidental child markets. Existing receipts, including embedded child observations, remain readable and unchanged. Direct market traversals still establish full catalogue coverage. Batching changes source endpoints, receipt and observation identities for newly acquired selections; provenance always names the actual request rather than a synthetic individual lookup. Metadata output preserves the operator's selection order.

Selected, dedicated-series and legacy exchange-profile protocol-5 parent hydration batches missing event tickers in deterministic groups of 20–100, bounded to 6,144 encoded initial-URL bytes. Small groups and URL-constrained tails remain singular. Ordinary events are queried first, then multivariate events for omissions, then singular lookups preserve authoritative 404/200 behavior; scoped ordinary-series captures skip the multivariate stage. Nested markets remain disabled. Every returned identity and applicable scope is validated, and parent batches never become reconciliation membership. Only successful results in the final pagination generation authorize a positive lookup, while native winner selection still compares all observations by `received_at DESC, observation_id DESC`. Actual batch receipt provenance is retained. A list omission never proves absence.

Protocol-5 historical list traversals retain every cutoff receipt and read a fresh boundary at start, after resume or cursor reset, after 100 data pages or a 300-second monotonic scheduler interval, and before terminal completion. The interval is checked before scheduling a logical page; limiter waits, retries and network latency may extend the time until a cutoff response arrives. It is not an atomic snapshot or a hard freshness SLA. Singular historical lookups retain a fresh cutoff per lookup. Failure to obtain a terminal cutoff leaves the traversal incomplete; resume reuses committed data receipts and obtains the required boundary before new data requests.

### Historical full-capture scope

New unselected, unscoped full captures acquire series, ordinary events and all historical
markets, including historical combos. They omit the live `/markets` and
`/events/multivariate` traversals. The protocol-5 `parent_policy: "historical-only-v1"`
seals this plan into the existing acquisition-policy checksum, request context, genesis and
snapshot checks. Older readers reject the unsupported sealed policy. This does not change
raw formats, journal framing, root storage version or the meaning of old captures.
Explicit legacy exchange captures, selected metadata and dedicated-series captures retain
their own plans. Historical captures verify their acquired evidence before completion but
do not acquire missing parent definitions; unresolved relationships remain visible.

An explicit historical build profile can also select completed series, ordinary-event and
historical-market tasks from an incomplete legacy capture. All selected primary tasks and
the terminal historical cutoff must be complete. The full source journal and snapshot are
validated; selected receipts retain their original capture/receipt provenance and are freshly
verified. This operation never changes the source capture's completion state or performs
network requests. Event-reference markets and excluded traversal observations cannot enter
the historical warehouse. History retains all selected generations; current membership uses
only final generations and winners still compare `received_at DESC, observation_id DESC`.

Historical builds share the Arrow/dbt projection, integrity-test, export and certification
machinery, with a distinct `builds-historical/<capture_id>` identity. Parent and combo-leg
availability do not remove historical markets. The database includes a
`main.catalogue_coverage` record identifying its historical scope and real source-capture
completion state. Internal build selector 3 is not a public catalogue-v3 contract.

Publication uses `oddsfox.kalshi.historical.v1`, `coverage_scope: "historical"` and
`current-historical.json`. Manifest and coverage bind the included/omitted scopes, selected
task indices and final generations, source completion status and root identity. Complete
exports, immutable file checksums and independent verification remain required. Historical
publications cannot become catalogue-v2 incremental baselines; historical delta composition
is not implemented. Legacy catalogue v1/v2 and series v1 contracts remain unchanged.
Replay, rebuild, retention and discard respect the historical publication's evidence closure.

`refresh --historical --capture-id ID` explicitly finishes a saved historical scope without
acquisition. Its verified workflow and scope may complete while `capture_complete` and
`source_capture_complete` remain false. Ordinary resume never implicitly changes a legacy
capture's sealed plan. User-authorized retirement of excluded raw bodies records a separate
`retired-scopes.json` guard; updated binaries reject ordinary network resume for that source.
Keep all selected evidence, manifests, journal/snapshot and any suffix bodies required for
replay. Retirement does not erase consumed requests/downloads or establish byte integrity of
the removed data. It intentionally ends full-exchange recovery and requires an auditable,
exclusive deletion list; it is not automatic retention cleanup.

### DuckDB 2 physical storage compatibility

The producer lock pins DuckDB 2.0.0, dlt 1.31.0, dbt-duckdb 1.11.1 and dbt-core 1.12.5; its supported dlt integration is the application's tested Arrow landing path, not a general upstream DuckDB 2 compatibility claim. DuckDB's physical storage version is independent of the application root marker (`storage_version: 5`), acquisition protocol and release contract. DuckDB 2 reads existing DuckDB 1.x databases; DuckDB 1.x readers cannot open the native v2.0 database files produced by DuckDB 2.

When a new build needs a native warehouse from a certified legacy database, it attaches the source read-only and uses [`COPY FROM DATABASE`](https://www.duckdb.org/docs/2.0/sql/statements/copy) to write a new staging file. Native DuckDB 2 sources retain the certified byte-copy path. Source databases and immutable releases are never rewritten. A completed certified legacy build is reused during resume; conversion requires an explicitly requested new build or rebuild from the existing capture and performs fresh certification. No conversion runs merely because the installed runtime changed.

Publication uses a private unnamed in-memory DuckDB connection and attaches the certified warehouse read-only. DuckDB 2 `COPY` can infer required Parquet fields from source constraints; publication disables `statistics_propagation` within that private database instance so the existing public fields remain nullable. The setting is per database instance, leaving native warehouse constraints and settings on other instances unchanged. Parquet writer settings and deterministic ordering are unchanged.

The export instance uses the existing `4GB` processing memory setting, which can affect when sorting spills; its temporary cap limits spill files only, so Parquet output plus sort spill can exceed root or temporary soft limits before post-export checks, with no hard quota added and the separate dlt limitation still open as `WORK-42`.

Conversion checks catalog inventory (including constraints, views and macros), compares every table as a row multiset in both `EXCEPT ALL` directions, detaches the source, validates view and macro resolution, checkpoints the destination and verifies its native storage version. These checks preserve the source warehouse's logical contents; the destination's physical bytes may differ.

The conversion reservation is not a hard output quota. DuckDB's `max_temp_directory_size` limits spill files only; `COPY` can grow the destination and WAL beyond the source-size reservation before post-copy storage accounting checks them. Root, temporary and database soft limits can therefore be exceeded before failed staging is cleaned up. The dlt post-load quota limitation remains separately tracked as `WORK-42`; this change adds no hard quota.

### Landing and incremental query work

Landing uses the existing dlt Parquet/DuckDB merge keyed by observation identity, with explicitly typed Arrow tables. Application batches flush at 4,096 rows or 8 MiB of logical UTF-8 field data; an oversized observation is emitted alone. The byte target is soft for that singleton, not a new evidence rejection threshold or hard memory quota. Scoped dlt lineage generation preserves compatibility with existing dictionary-created warehouses, and extraction/normalization buffers flush each yielded batch. Configuration is restored after success or failure.

The 13 logical landing columns retain text types and nullability. Provider timestamp conversion retains the dictionary loader's logical results; complex values remain in the complete native payload with a null projected timestamp. Physical database bytes and dlt internal identifiers are not public release identities. The documented dlt post-load storage-quota limitation remains.

Incremental current-entity winner windows restrict their input to affected keys while reading all history for each key. Required-parent membership, dependency discovery, full integrity tests and complete exports remain unchanged. Full-mode query branches retain their existing behavior.

### Catalogue versions and selection

Catalogue v1 remains `oddsfox.kalshi.catalogue.v1`, published through `current.json`. Full capture remains the default. Default `load`, `build`, `publish` and metadata capture selection excludes incremental captures, even if a delta is newer. Targeted captures remain separate from catalogue captures.

Opt-in `capture --incremental` pins a certified v2 publication when present, otherwise a certified v1 baseline. Building or publishing a composed capture requires its explicit capture ID. Composed output uses `oddsfox.kalshi.catalogue.v2` and `current-v2.json`; promotion leaves `current.json` untouched. A verified full capture published as version 2 establishes a new baseline.

`current`, `replay`, `rebuild` and `publish` accept `--catalogue-version 1|2`, defaulting to 1. `verify --release` dispatches from the supplied manifest contract. Metadata v1 export rejects incremental captures instead of exporting only their changed subset. Full exports, checksums and independent release verification remain required for both catalogue versions. A pre-existing release destination must match its contract and capture identity as well as its verified files.

A v2 manifest additionally carries `root_id`, `baseline_release_id`, `baseline_manifest_sha256`, `baseline_capture_id`, `previous_watermark`, `watermark_started_at`, `delta_depth` and `membership_sha256`. Baseline fields name the immediate pinned predecessor for a delta and are null for a full rebase. Full depth is zero; each delta increments depth. The membership digest commits sorted scope/entity-kind/native-ticker entries, including membership not visible in the current relations. These fields are also included in v2 coverage, binding them into the release identity. Publication pointers contain the release ID and manifest checksum.

Every release contract binds `capture_id` and `coverage_scope` from its single-row coverage relation to the manifest: catalogue v1/v2 require `catalogue`, and series v1 requires `series`. Verification reads only the bounded primitive columns after checking the file inventory, and rejects missing columns, invalid types, extra rows or mismatched values. V2 and series v1 additionally bind all eight lineage fields; series v1 also binds its ticker and `include_multivariate` flag. Publication time and the optional physical warehouse checksum are outside this coverage binding. This strengthens standalone verification without changing compatible release bytes or schemas.

New v2 manifests also record the optional `warehouse_sha256` of the freshly certified, checkpointed database. It is a verification hint outside the release identity and coverage fields. Matching freshly verified database bytes avoid a repeated semantic comparison; a missing or different hash requires schema, row-multiset and membership equivalence against the pinned release. Existing v2 manifests remain valid and immutable. V1 manifests do not gain this field.

### Coordinated refresh results

`refresh [--full | --capture-id ID]` is an additive catalogue-v2 workflow. It uses existing capture/build/publication checkpoints and one operator lock and deadline; it adds no storage, journal, receipt or acquisition format. Default invocation requires a verified baseline, preferring v2 with the existing v1 fallback. Full acquisition and rebasing require explicit `--full`; eight deltas never trigger an automatic rebase. Targeted captures cannot be resumed through this command. Existing capture, publication and metadata commands retain their selection defaults and result schemas.

The new workflow result distinguishes whole-operation `complete`, nullable `capture_complete`, allocated `capture_id`, nullable `resumable`, stage, publication state and acquisition accounting. Stages are `preflight`, `capture`, `publication`, `complete`; publication includes build, export, verification and pruning. Publication state is `not_attempted`, `verified` or `unknown`. Unknown counts remain null with incomplete accounting. An allocated ID does not prove durable genesis. Successful completion includes the verified release identity and output directory. All expected operational failures, including setup and final reconciliation, retain one structured result and the known identity. Argument-parser errors retain normal argparse behavior.

A budget stop returns exit 3 even when acquisition completed. Other invariant/input failures return exit 1. Publication/cleanup failure may follow pointer promotion and reports unknown state rather than promising rollback; retrying the same explicit ID follows existing recovery. The v1 pointer remains untouched. Workflows do not run automatic capacity probes or increase the configured rate; protocol-5 capture may reduce its invocation-local rate after HTTP 429. Evidence verification is unchanged.

### Incremental acquisition and freshness

Each incremental capture seals a UTC start watermark before its first request. Its ordinary-event and supported non-combo market metadata queries begin at the previous published watermark minus a fixed 300-second overlap. Series, combo events, combo markets and historical markets are fully reconciled on every composed refresh. The watermark advances to the sealed start only after verified publication. Resume retains the original baseline, watermark and query window even if another publication appears.

The first delta from a v1 baseline seeds its previous watermark from that full capture's UTC `started_at`. A full v2 rebase uses the same seed. Completion or manifest timestamps would miss changes made during the baseline traversal.

Overlap deduplicates an observation already identified by the same receipt and observation identity. Distinct receipts remain distinct historical observations; equal ticker or payload values alone are not a deduplication key. Every historical-cutoff receipt remains part of the evidence history, including cutoffs before subsequent historical reads.

Metadata-update filters are not a universal change feed. Trading-only values such as price, volume and open interest may be carried from the baseline with their actual observation timestamps. Updates arriving outside the overlap may require full reconciliation or rebase. Coverage describes the acquired scopes and interval; it does not claim a fresh atomic snapshot of all values.

### Membership, projections and provenance

A composed build copies the certified, checkpointed baseline warehouse into staging. The published baseline is immutable. New observations land idempotently; affected current entities, relationships and dependent combo legs are updated, and full integrity tests still run.

Membership is an explicit input to current projections, distinct from observation history and parent-resolution lookups. A completed full reconciliation replaces only its own scope's membership. If a traversal resets its cursor, only its final completed cursor generation establishes replacement membership; earlier receipts remain observations and evidence. An incomplete traversal cannot remove members. Omission from a delta removes nothing.

Applicable live and historical market memberships are combined before resolving current markets. Removal from current membership retains observation history; reappearance can restore membership. Parent hydration resolves declared relationships without claiming that a lookup enumerated an entire reconciliation scope. Reassignment updates the affected relationship and dependent combo legs.

Current events include listed event membership plus authoritative parents of active markets positively resolved during this capture. Current series include listed series membership plus authoritative parents of active events positively resolved during this capture. A prior observation alone is not a successful fresh parent lookup; a 404 does not restore parent eligibility. Lookup-only parents reachable solely from inactive historical rows do not become permanent members. Removing historical membership does not remove a market still retained by live membership; delta omission supplies no live tombstone, so authoritative removal in that case requires a full rebase.

Current winners remain `received_at DESC, observation_id DESC`. Provider timestamps never silently replace that order. Direct market definitions remain authoritative over event-embedded references. Carried and new rows retain their original source capture, receipt and observation provenance; carried evidence is never relabeled as newly acquired.

Full v2 baselines project the final completed cursor generation's memberships into their own certified warehouse under `builds-v2/<capture_id>`; the v1 warehouse remains unchanged. When a legacy full capture lacks fresh parent-resolution evidence needed by that projection, a new full capture is required. A direct v1 bootstrap preserves the pinned v1 current ordinary events and live non-combo markets with successful non-singular list evidence, including earlier cursor generations; singular hydration and history-only markets cannot seed those scopes. This preserves the selected baseline's semantics until a scope is explicitly reconciled.

Baseline copying requires a closed, checkpointed certified warehouse. Rebuilding the same baseline may change database bytes; accepting that rebuild still requires fresh certification, schema and row-multiset equivalence against the pinned immutable release, and equivalent membership state. Published source databases are never opened for writable checkpointing. Carrying a baseline does not relabel its evidence as newly acquired.

### Ancestry, retention and discard

A composed baseline permits at most eight delta captures. Another delta requires a verified full rebase. Missing, cyclic, corrupted or cross-root ancestry is rejected before build or publication.

Retention preserves the complete evidence closure reachable from both publication pointers and incomplete captures. Incomplete captures stay pinned indefinitely unless explicitly discarded. Retained completed compositions also keep their referenced ancestry. Completed captures at or after the relevant full baseline start remain candidates for publication; an older unreachable group may be pruned together, with children retired before parents. No incomplete recovery pin expires merely because time elapsed.

Explicit discard is allowed only for an incomplete capture that no publication or descendant references. Pruning computes the retained dependency closure before deleting anything, and removes obsolete dependencies only after successful verification and promotion. A failed build, verification or promotion cannot prune evidence needed by either publication or recovery.

### Ordinary-series releases

A dedicated root fixes exactly one descriptor: `{"kind":"series","series_ticker":"KXCPI","include_multivariate":false}`. The selected ticker is validated rather than hardcoded. New scoped roots use `root.json` with the existing owner, `storage_version: 5` and this `scope`; new ordinary roots also use storage version 5. Existing storage-version 1–4 roots remain readable and require explicit `upgrade-root` before writing; version 3 was the former ordinary format and version 4 the former scoped format. Upgrade preserves the exact scope and root identity and never converts an ordinary root to a scoped root or vice versa. Initialization requires a new empty directory and installs the marker under the canonical writer lock. Competing initializers cannot replace another scope or an ordinary marker. Writers recheck the exact descriptor after locking. If initialization stops before the marker, an unowned directory containing a lock file fails closed; preserve it and use a fresh directory.

New scoped captures use acquisition protocol 5; protocol 4 remains readable for existing scoped captures and resumes with its original settings. Genesis, immutable journal settings, snapshots, request identities, usable receipt contexts, certification and baseline pins bind the scope and logical root identity. Missing fields, extra fields, non-boolean multivariate flags, changed tickers, incompatible copied captures and unsupported contracts fail closed. Journal framing, raw formats and raw → receipt → journal → state durability remain unchanged. Existing ordinary and scoped captures retain their original protocols and request parameters.

Both baseline and subsequent refresh acquisition enumerate `/series/{ticker}`, `/events?series_ticker=S&with_nested_markets=false&limit=200`, `/markets?series_ticker=S&mve_filter=exclude&limit=1000` and `/historical/markets?series_ticker=S&limit=1000`, plus the existing historical-cutoff protocol. Every cursor is followed, without status or update-time filters. No global series or multivariate traversal is used. See Kalshi's [events](https://docs.kalshi.com/api-reference/events/get-events), [markets](https://docs.kalshi.com/api-reference/market/get-markets) and [historical markets](https://docs.kalshi.com/api-reference/historical/get-historical-markets) contracts. During live acceptance the historical endpoint rejected combining `series_ticker` with `mve_filter` as mutually exclusive, so its scoped query uses the series filter alone; strict ordinary-event and combo validation still applies.

The singular series must exist and match. Events must identify the selected series and cannot carry combo payloads. Current markets must resolve through authoritative event definitions, not ticker prefixes. Missing, contradictory or out-of-scope parents preserve evidence but prevent publication. Fresh proof covers parents required by retained-history winners as well as incoming observations, including equal receipt times and clock rollback. Singular event hydration suppresses incidental children. Only final pagination generations replace membership; earlier verified observations remain history and cutoff history stays complete.

Scoped refreshes use certified predecessor copies and the existing Arrow, affected-key, relationship and full-integrity machinery. Unlike exchange-wide metadata deltas, every completed series membership scope is replaced, including live events and markets. Combined live/historical membership determines current markets. Observation history, exact decimals, source provenance and last-observed/direct winner ordering remain unchanged. Distinct newly fetched receipts create observations even for unchanged objects; identical-receipt replay is idempotent. There are no metadata-update windows or `query_from` fields. Lineage timestamps remain for ordering and certification, not filtered acquisition.

The public contract is `oddsfox.kalshi.series.v1`, through `current-series.json` only. It reuses the internal v2 warehouse layout and deterministic relations without creating catalogue v3. Manifest and coverage both bind `coverage_scope: "series"`, `series_ticker` and boolean `include_multivariate: false`, alongside the existing lineage fields; the manifest also carries `series_scope`. Standalone `verify --release` dispatches explicitly by contract and checks this binding. Unknown contracts never fall through to catalogue v1. Series baseline selection has no catalogue-v1 fallback. All ancestry must have the same contract, root identity and exact scope.

`series refresh --series-ticker S --full` initializes the baseline. Later `series refresh` reconciles it; `series refresh --capture-id ID` resumes its exact settings and pinned predecessor. `--full` and `--capture-id` conflict. Results use the existing refresh stage/publication/accounting/exit semantics plus `series_scope`; an allocated capture ID alone does not prove durable initialization. One writer lock and deadline cover all stages. Completed resume avoids networking and redundant landing while retaining fresh verification. `series current`, `series replay [--capture-id ID]` and `series rebuild` select the series publication; replay/rebuild do not publish. Generic status and discard remain scope-aware, while ordinary catalogue and metadata producer commands reject these roots.

Eight refresh captures require an explicit full rebase before another. Retention protects the series publication closure and incomplete pins, with no time-based expiry. A verified promotion may prune obsolete unreferenced ancestry after rebasing; it does not promise permanent history beyond protected ancestry. Cleanup can fail after pointer promotion, so unknown publication state requires inspection/retry, not assumed rollback. Preserve the root on committed corruption. Older binaries reject version-5 operator roots before writing; existing consumers of the `oddsfox.kalshi.series.v1` release contract remain compatible. Rollback uses a separate compatible root and retained verified publication, never a downgraded marker.

Coverage remains `atomic_snapshot: false`. Kalshi separates live and historical market tiers while events and series stay at their original endpoints ([historical-data documentation](https://docs.kalshi.com/getting_started/historical_data)). A handoff during separate paginated reads can change visibility. Completed traversals certify the declared scope over the observation interval, not an atomic exchange snapshot or exposure of every historically existing record. Further reconciliation may be needed near a handoff. Incremental persistence does not reduce series acquisition work or guarantee a faster build; complete exports and verification remain required.

### Deterministic output and verification

Certified output proves the export keys unique: native ticker for current series/events/markets; observation ID for history; combo market ticker and leg index for combo legs; parent kind/ticker and child kind/ticker for relationships. Publication orders by those explicit keys, preserving existing lexicographic order where they are already a unique prefix. Payloads, decimal types, relation schemas and Parquet writer settings remain unchanged for compatible full-mode output.

Within one command, evidence validation, hashing, decoding, landing and inventory collection may share verified input bytes. That reuse is operation-local. The private full-capture index described above may persist as a derived hint across resumes, but it does not cache authoritative proof or satisfy a verification boundary. Publish freshly verifies build evidence and checksums, while standalone verification remains independent and complete. Mutation between commands must prevent publication. Metrics and benchmark reports stay outside command-result JSON, evidence, release identities, Git and distributions.

### Diagnostic partition evidence

The manual throughput probe can acquire explicitly selected ordinary-series and multivariate-collection event partitions into fresh ordinary operator roots. These are diagnostic receipts, not captures: no genesis, snapshot, page journal, warehouse, release or publication pointer is created. Receipt context uses diagnostic identifiers and cannot satisfy production capture/task identities. Normal build, replay, metadata export and publication cannot select this evidence. The pilot is non-resumable; preserve incomplete evidence and use a new output directory for another experiment.

Ordinary partitions use `/events?series_ticker=S`; multivariate partitions use `/events/multivariate?collection_ticker=C`. Both request 200 events per page, disable nested markets and follow all returned cursors without status/update filters. One shared client, limiter and budget serve at most eight workers, with at most one request outstanding per partition. Repeated cursors, malformed envelopes or identities, contradictory scope and unexpected statuses stop the experiment; this pilot does not reset cursors.

Preflight retrieves each selected collection definition once and binds its native ticker and series to the shared selection. Returned ordinary events must match their series; collection-filtered events must match the declared series and any supplied collection identifier. Collection membership remains a provider-filter assertion, not independent certification. Constituent `associated_event_tickers` do not establish generated-event membership. Duplicate observations and payload variants remain in diagnostic inventories; fingerprints distinguish numeric decimals from equal-looking strings and canonicalize object-key ordering. An incomplete traversal never proves absence.

Report version 2 identifies the throughput profile; existing screening reports retain version 1. Diagnostic verified pages are distinct from production journal-committed pages. Malformed or out-of-range worker reports stop further samples with unavailable accounting; unrepresentable derived rates are null. Reports and metrics are external to catalogue contracts, evidence identities and distribution contents. No storage version, acquisition protocol, release schema or production traversal changes through this pilot.

## Production database entry point

The manual production runner manages a dedicated directory containing an ordinary `operator/` root, session reports under `runs/`, and `production.duckdb`. In source-checkout context it accepts only strict descendants of the canonical project's ignored `data/` directory; it rejects external write destinations, the checkout root, the `data/` container itself, other source-tree paths and symlink ancestors. The project checkout is distinct from a frozen runtime's code root. Frozen source tools require canonical checkout working-directory context or the validated absolute `KALSHI_EVENTS_PROJECT_ROOT` binding; child processes inherit that binding. Operator data remains excluded from Git and distributions. Its bookkeeping is external operational state: existing root versions, acquisition protocols, receipts, catalogue v1/v2, metadata v1 and series v1 remain unchanged. Existing catalogue commands do not implicitly activate this entry point.

Relocate a managed directory only after all writers have stopped and its canonical locks can be acquired. Move the complete tree on the same filesystem to preserve file identities and hard links. Preserve logical root IDs, capture state, immutable manifests, original accounting and deadlines; record an old-to-new path mapping instead of rewriting historical provenance. Resume locates the existing session by capture ID and creates new invocation log paths beneath the supplied directory. Runtime code and virtual environments can remain external.

Production activation requires successful refresh cleanup, standalone verification of the exact release, and fresh warehouse certification under the canonical writer lock. The selected historical or legacy v2 publication must still identify that expected release. If the freshly computed database hash matches the manifest's optional `warehouse_sha256`, the report's `verification_mode` is `warehouse_hash`; if the hint is absent or differs, the mode is `semantic` and activation proves schema, row-multiset and membership equivalence against the pinned release. It records the actual database hash and manifest hint separately; this fallback does not rewrite an existing immutable manifest. Both source and destination WAL files are forbidden. A same-filesystem temporary hard link is atomically renamed to `production.duckdb`, followed by directory synchronization and file readback. No evidence-directory symlink exception or permission change is introduced.

The entry point and its warehouse share an inode and immutable contents. Consumers must use DuckDB 2.0 or newer and open the database read-only; DuckDB 1.x cannot open native v2.0 storage files. Public Parquet releases remain a separate engine-independent handoff. Existing readers retain their opened generation across replacement. DuckDB may reuse the old database instance for additional connections to that path in the same process; close all connections to the path before reopening, or use a fresh process to obtain the new generation. The link survives removal of its original warehouse pathname, but does not extend raw-evidence retention or independently certify deleted evidence. Session storage accounting counts unique device/inode pairs and includes the production file after its original pathname disappears. Files held open after unlink can consume additional disk space; the minimum free-space check remains necessary.

Production memory telemetry has an invocation-specific effective-policy version, separate from root, acquisition and release versions. Historical `system_compressed_bytes` values remain logical uncompressed contents represented in the system compressor; physical occupancy is reported separately. The former absolute logical cutoff is no longer enforced. The current pressure policy accepts only userspace flags 1=NORMAL, 2=WARN and 4=CRITICAL, checks NORMAL before processing, and stops on the first observed CRITICAL or 60 continuous seconds of WARN. NORMAL or a gap greater than 22.5 seconds resets the warning timer. Existing process-group RSS limits, resource caps, clocks and termination guarantees remain in force. Missing or malformed telemetry fails closed. The pressure sysctl is private and version-sensitive, so capability checks are required on each run.

Resource samples have a bounded 256-entry inline tail and aggregate counts/peaks; truncation preserves the previous report in run evidence. Resume records the previous stop separately before clearing the new attempt's error and recovery fields. Offline invocation request/download counts remain zero independently of conservative lifetime acquisition accounting. New progress phases and aggregate landing counters are operational diagnostics only and do not change command-result or release identities.

Abandoned historical staging is disposable only after replacement recovery and validation under the canonical writer lock. Cleanup is restricted to direct managed UUID staging names and rejects symlinks, cross-device entries, special files and multiply-linked regular files. It never prunes raw evidence, captures, public builds, replacement backups or recovery caches. Root/temporary/database quota checks run against the post-cleanup accounting. The independent 150 GiB minimum-free-space gate remains in force before processing; cleanup does not bypass it. This does not provide hard enforcement for every dlt write.

Acquisition completion, operator publication and production activation are separate states. A failure before replacement preserves the prior production link. A failure after replacement can leave activation uncertain even when the new file is present; reports must not claim rollback. Recovery verifies actual database hashes and the expected publication instead of trusting a prior status string. `--activate-current` performs offline verification, completes the current verified publication's existing retention cleanup under the writer lock, and then activates it; it does not acquire, build or silently resume a capture.

`--historical --capture-id ID` is the saved-evidence-only production path and
`--activate-current --historical` selects historical activation. A separately authorized
`--offline-duration-seconds` of at most 86,400 creates an immutable, capture/root/revision-bound
`offline_historical_window` after preflight. Historical processing uses this window through
build, export, standalone verification and activation, even if the original networking
workflow/session period has expired. Existing network deadlines, counters and consumed
extension history remain unchanged. A repeat invocation reuses the recorded window and
cannot reset it. Network/full modes reject this option; no acquisition can use its allowance.

An expired window can be replaced only by a separately authorized invocation with
`--historical --capture-id ID --offline-duration-seconds SECONDS --renew-offline-window`.
New grants use operational-window version 2, with a duration of at most 86,400 seconds
(24 hours). Existing version 1 grants remain valid only through their original maximum of
14,400 seconds (four hours). Both versions use the same closed field set; each current or
historical window is checked against its own version's limit. Unknown versions and boolean
version values are rejected. New initial grants and explicit renewals write version 2;
ordinary reuse preserves the existing record and deadline, even with a larger requested
duration. These are operational report versions, not new root, acquisition or release formats.
Renewal rejects unexpired windows, active or
unreconciled children, already activated sessions, incompatible boots/volumes and mismatched
production-owner/operator-root identities. The prior grant must be structurally valid and
expired on both wall and monotonic clocks. Its revision remains provenance and may differ
from the new verified source revision. The existing grant is appended unchanged to
`offline_historical_window_history`, and the new grant is persisted atomically before child
work. History must retain matching capture/root bindings, bounded durations and ordered,
nonoverlapping windows. This operational history is not catalogue certification evidence.
Acquisition counters, original session clocks, resource limits and consumed acquisition
extensions are not reset. The option cannot accompany acquisition, activation-only,
accounting reconciliation, session extension or reboot recovery. Ordinary invocation
without renewal retains the existing expiry and revision checks.

An operator may explicitly replace a grant before both clocks expire by using
`--supersede-offline-window` with the same historical capture and duration arguments. It
implies renewal and retains the prior grant unchanged in history. A separate strict
supersession record binds the archived grant's exact bounds to its successor's start;
history validation permits overlap only for a matching record. The stopped-session,
identity, writer-lock, boot and volume checks remain required, and no acquisition budgets
or counters are reset.

The full-run supervisor retains the effective approved session deadline and cumulative invocation consumption across ordinary explicit exact-capture resumes. Each child receives an immutable UTC stage deadline before dispatch; active monitoring checks both that deadline and its monotonic deadline, including the termination reserve and resource-check timeouts. Neither a forward wall-clock change/forced sleep nor a backward wall-clock change grants additional runtime. Pruning retained receipts must not reduce the session's request/download totals. Unverified or unbounded consumption, expired networking allowances, contradictory capture identities or an unreaped worker prevent subsequent acquisition. Progress reporting never restarts a child or extends the deadline. Ordinary explicit resume retains the effective approved clock and cumulative limits. The one-time `--capture-id ID --reconcile-accounting --extend-session` flow can consume a new 48-hour window; it records old/new deadlines before preflight and preserves cumulative request, download and storage ceilings. Production-path activation never represents an atomic exchange snapshot: the verified release retains its real observation interval and `atomic_snapshot: false`.

Accounting reconciliation allows only the recorded legacy lock/runtime to the current lock/runtime, or current to current. The legacy allowlist is DuckDB 1.5.6, dlt 1.31.0, dbt-core 1.12.5, dbt-duckdb 1.11.0, PyArrow 26.0.0, httpx 0.28.1 and httpcore 1.0.9; the current allowlist changes DuckDB to 2.0.0 and dbt-duckdb to 1.11.1. Both the saved and current lock hashes, exact package versions, pinned HTTP transport source and 64 KiB raw-read bound must match the allowed transition. The transport allowlist accepts the known pre-pacing-fix source, the source before typed body-JSON validation, or the current source transitioning to the current implementation; unknown source hashes remain blocked. Typed body-JSON errors are classified only after raw integrity validation; the HTTP request accounting and 64 KiB read bound are unchanged. Historical reports under the legacy lock may omit saved `dbt-duckdb` or `httpcore`; other missing or mismatched values block networking. A runtime transition preserves the original effective deadlines and cumulative request, download and storage ceilings; changing runtimes grants no new time. The separate one-time session extension requires its explicit recovery flags and does not reset cumulative ceilings.

When `--metrics-file FILE` is enabled, the refresh worker writes the sibling `FILE.progress.json` companion. Version 1 has `version`, fixed `phase` (`preflight`, `recovery_validation`, `first_new_request`, `index_replay`, `closure`, `complete` or `stopped`), monotonic `elapsed_seconds`, UTC `updated_at`, and fixed aggregate counters `journal_records`, `total_pages`, `indexed_pages`, `backlog_pages`, `reused_pages`, `verified_pages`, `first_data_request_elapsed_seconds` and `first_data_page_elapsed_seconds`. The first-request value is captured immediately before the first non-cutoff HTTP attempt, after limiter and cooldown waits; the first-page value is captured after its data page is committed. It writes initial/final snapshots and phase changes immediately; same-phase progress calls write only when at least 15 seconds have elapsed since the previous progress write. The elapsed values are worker-local and exclude supervisor preflight and process startup; `session.json` separately records `metrics_progress_file` plus supervisor `preflight` and `accounting` durations. The final metrics report also has fixed aggregate `recovery_cache_enabled`, `recovery_cache_reused` and `recovery_cache_invalidated` counters; the progress `reused_pages` count remains a provisional hint count. No request or ticker labels are stored in these reports.

Explicit `--capture-id ID --reconcile-accounting` recovery can establish a conservative download bound when exact consumption is unavailable. It accepts an abrupt unknown-accounting stop or a resolved compressed-memory, RSS, free-space or persistent process-group RSS sampling timeout stop. A transient `ps` timeout is retried once within the same five-second probe budget; if that retry also times out, the supervisor stops and reaps the child without recording an RSS sample and reports `resource accounting failed: process-group RSS sampling timed out`. Malformed output and an empty result for a live group remain ineligible. The exact legacy system-wide `ps` timeout report is also accepted for existing sessions. A fresh locked scan validates the original capture and every attempt; each unfinished request is charged the full sealed response ceiling plus a 64 KiB transport-chunk allowance. Before recovery proceeds, the supervisor enforces the exact lock/runtime/transport allowlist above, including permitted missing package metadata only for historical reports under the legacy lock. The prior system snapshot is retained as `original_system`, while `system` records the recovery environment. Exact downloaded bytes remain unavailable, and raw receipts are never rewritten. The root and filesystem remain binding, along with the effective approved wall deadlines and cumulative budgets. Ordinary recovery also requires the original boot. Explicit `--recover-reboot --recovery-volume-uuid EXPECTED_VOLUME_UUID` requires exact-capture accounting reconciliation and a stopped session with no unreconciled child marker; it cannot accompany `--extend-session`. The expected canonical volume UUID must match bounded macOS volume metadata; the volume mount must contain the production directory and share its device with the operator root. A saved UUID, when present, must match. For legacy reports without one, the audit records explicit current-volume selection rather than claiming historical physical-volume proof. Same-boot and active-run device checks remain unchanged. It records the old boot/clock mapping and rebases monotonic start/deadline values from the unchanged epoch values before any child starts. This does not refresh a budget or consumed extension; expired wall deadlines and backward clocks remain fatal. Integrity, origin, mount, unreaped-worker and other unrecognized failures cannot use this exception. Every resource probe rechecks both clocks before using the remaining time outside the five-second termination reserve.

## Repository-owned data paths

Source-checkout command writers confine operator roots, metadata outputs, metrics/progress, production directories and probe/benchmark output to strict descendants of the canonical checkout’s ignored `data/` directory. Default operator state is `data/operator`, independent of working directory; diagnostic and benchmark runs use separate new destinations under `data/`. The data container itself cannot be a root or output. Input-only standalone verification may read external bundles and releases. Standalone installed consumers without checkout context retain caller-selected storage; low-level library `Store` is not a filesystem sandbox.

Temporary response spools, atomic writes, metadata staging, DuckDB spill and dlt pipeline state remain colocated with their selected root/output. Checkout no-root dbt scratch stays beneath repository data and is removed after use. Runtime environments and isolated installed-package verification environments remain separate from retained datasets. This path policy changes no evidence format, logical root identity, release contract, resource accounting or durability guarantee. Existing running frozen workers are not altered; migrate their data only after quiescence.


### Compact historical physical layout

The compact historical path is limited to newly created historical warehouses. It preserves the existing historical release contract, logical landing columns, public schemas, observation identities, exact JSON text, timestamps, decimal values, membership generations and direct-definition authority. Existing warehouses and releases are immutable. Catalogue v1/v2, metadata and series loading remain on their existing paths.

Native loading uses the existing bounded Arrow batches, a fresh database and native Zstandard VARCHAR storage for payload_json. Receipt verification remains mandatory. Repeated identical references to one immutable page may be emitted once; contradictory identity bindings fail closed, and distinct page/pointer observations are retained regardless of ticker or payload equality. Interrupted uncertified builds restart from saved receipts; partial loading is not a recovery checkpoint.

Historical observation history and current public relations may be views sharing canonical payload storage. Narrow current selections preserve received_at DESC, observation_id DESC, membership, parent eligibility, combo ordering and exact DECIMAL(38,18) conversions. Read-only consumers require no application UDF, external dataset or extension. New historical exports use lossless Zstandard level 6; changed physical bytes legitimately derive new checksums and release IDs. This is the historical exception to earlier unchanged-writer-settings guarantees.

Storage monitoring uses verified baseline accounting plus measured mutable workspaces. Database and WAL bytes count together; a database under tmp also consumes temporary allowance. The 56 GiB protective threshold and per-batch checks mitigate the 64 GiB ceilings, but neither polling nor DuckDB's spill-only max_temp_directory_size is an aggregate hard quota. Record actual sample gaps and overshoot; missing or unsafe accounting fails closed. WORK-42 remains separate.

Stopped-worker reconciliation is explicit and historical-only. Preserve the saved failure and process evidence; validate root, boot, capture, locks and absence of the original owned processes before clearing stale process state. Group absence observed later does not establish that the supervisor previously reaped the child. A new offline grant preserves all old grants, consumed extensions and lifetime reserved-upper-bound accounting. No networking or automatic retry is permitted.
